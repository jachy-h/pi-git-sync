# pi-git-sync v0.3.0 API 简化方案

> 状态：Draft
>
> 版本主题：用一个默认动作完成初始化或双向同步，降低用户理解和操作成本。

## 1. 背景

当前写操作分散在三个子命令中：初始化使用 `/pisync init`，获取远端配置使用 `/pisync pull`，提交本机配置使用 `/pisync push`。无参数的 `/pisync` 只打开操作菜单。

这套 API 要求用户先判断当前状态，再理解同步方向并选择命令。实际上，大多数场景只有两个用户意图：

1. 第一次使用时连接配置仓库；
2. 日常使用时让本机与远端收敛到一致状态。

v0.3.0 将这两个意图统一到 `/pisync`。

## 2. 版本目标

1. 用 `/pisync` 替代初始化子命令；首次执行时引导用户输入 Git URL 并完成现有初始化流程。
2. 已初始化时，`/pisync` 固定执行“先拉取、再推送”的完整同步流程。
3. 从命令注册、补全、菜单、帮助和 README 中移除 `init`、`pull`、`push` 三个操作子命令。
4. 保留 `/pisync status` 和 `/pisync diff` 作为只读诊断命令。
5. 不降低现有冲突保护、Secret 扫描、Package 审批、备份回滚和多设备分支安全性。

## 3. 非目标

- 不改变 `pi-sync.json` 或 `state.json` schema。
- 不重写 capture、三方比较、materialize、Package 安装或 Git 合并算法。
- 不增加后台自动同步、定时同步或 session 生命周期自动同步。
- 不在本版本提供重新初始化、切换远端或 reset 的新公共命令。
- 不保留旧写命令的兼容别名；v0.3.0 是明确的命令 API 切换。

## 4. 产品方案

### 4.1 v0.3.0 公共命令面

| 命令 | 类型 | 行为 |
| --- | --- | --- |
| `/pisync` | 写操作 | 未初始化时执行初始化；已初始化时执行 pull phase → push phase |
| `/pisync status` | 只读 | 显示仓库、分支、ahead/behind、冲突和本地状态 |
| `/pisync diff` | 只读 | 显示待同步差异 |

不再注册、展示或补全以下形式：

- `/pisync init`
- `/pisync pull`
- `/pisync push`
- `/pisync push --continue`

`pull` 和 `push` 可以继续作为内部技术阶段名称，但不再是用户可调用的命令。

### 4.2 无参数命令的状态分派

`/pisync` 根据本地生命周期状态分派：

| 状态 | 判定 | 用户结果 |
| --- | --- | --- |
| 未初始化 | 没有有效的 repo state 和配置仓库 | 提示输入 Git URL；取消输入时不产生任何变更 |
| 已初始化 | state 指向存在的 Git 仓库，且包含有效 `pi-sync.json` | 执行完整同步 |
| 初始化损坏 | state、仓库目录、`.git` 或配置文件只存在一部分 | fail closed；给出修复提示，不覆盖或重新 clone 可疑目录 |
| 有待恢复操作 | `pendingOperation` 非空 | 先进入恢复分支；恢复成功后再继续正常同步 |

首次初始化只执行当前初始化职责，不在同一次调用末尾额外执行第二轮同步。之后每次 `/pisync` 才进入完整同步流程。

### 4.3 初始化体验

用户只需要输入：

```text
/pisync
```

未初始化时：

1. 状态栏显示 `Checking pi-sync status...`；
2. 弹出 Git URL 输入框；
3. 用户取消时提示 `Setup cancelled.`，不创建或修改仓库；
4. 用户提交 URL 后，继续使用现有 URL 校验、clone/scaffold、配置应用、Package 审批和 reload 逻辑；
5. 成功提示使用 `Setup completed.`，不再暴露 `init` 术语。

v0.3.0 不提供公开的 URL 位置参数和 `--force`。这可保证默认命令只有一种稳定写法，并避免误触发破坏性重建。远端切换和强制重建后续单独设计。

### 4.4 日常同步体验

已初始化时，`/pisync` 的产品语义固定为：

```text
preflight → pull phase → push phase → reload once
```

用户看到的阶段进度建议为：

1. `Checking sync state...`
2. `Pulling remote changes...`
3. `Applying remote changes...`（仅需要时）
4. `Capturing local changes...`
5. `Pushing local changes...`
6. `Sync completed.`

“先 pull、再 push”是用户可观察的阶段顺序。为避免丢失本机未同步配置，pull phase 仍可在获取和合并远端之前创建本机快照或本地提交；这是 pull phase 内部的安全步骤，不改变产品语义。

### 4.5 阶段结果与停止规则

| pull phase 结果 | push phase | 最终行为 |
| --- | --- | --- |
| 成功且有远端变化 | 执行 | 应用远端后推送最终本机状态 |
| 已是最新 | 执行 | 仍检查并推送本机变化或已有 ahead commit |
| 需要 Package 审批 | 暂停 | 用户审批后重新校验并继续；拒绝则不 push |
| 冲突或校验失败 | 不执行 | 保留可恢复状态并提示处理方式 |
| fetch/pull 失败 | 不执行 | fail closed，避免在未知远端状态下 push |

push phase 失败时保留现有本地 commit，不回滚已经安全应用的远端变化。最终提示必须分别说明 pull phase 和 push phase 的结果，避免把“拉取成功但推送失败”显示成模糊的整体失败。

### 4.6 无变化

当远端、本地和仓库都没有变化时：

```text
Sync completed. Already up to date.
```

即使工作树无变化，push phase 仍必须检查当前分支是否已有 ahead commit。不能仅凭“没有未提交文件”跳过远端分支同步。

### 4.7 冲突恢复

v0.3.0 不再要求用户记忆 `push --continue`。统一恢复方式为：

1. 按提示在 Git 仓库中解决冲突并完成必要的 `git add`、`git rebase --continue` 或 merge；
2. 再次执行 `/pisync`；
3. 系统根据 `pendingOperation` 和 Git 状态决定继续未完成操作，还是提示仍需处理的文件；
4. 恢复成功后进入正常同步流程。

迁移自旧版本的 `push-rebase-conflict` pending state 必须继续可恢复，不能因为移除公共子命令而成为死状态。`apply-failed` 则通过同一个 `/pisync` 重试 apply 和后续同步。

### 4.8 参数、补全与错误反馈

- 无参数：执行 setup 或 sync，不再打开菜单。
- `status`、`diff`：按原语义执行。
- 其他参数：明确返回未知参数错误，不回退到菜单，也不静默执行同步。
- 旧命令输入：不作为兼容别名执行；只提示 `v0.3 uses /pisync for setup and sync.`。
- 参数补全：仅提供 `status` 和 `diff`。

未知参数必须 fail closed。这样 `/pisync pus` 之类的拼写错误不会意外触发完整同步。

### 4.9 reload 规则

一次 `/pisync` 最多调用一次 `ctx.reload()`：

- setup 成功且配置发生应用：末尾 reload；
- 完整同步中任一 apply 改变 agent：全部可执行阶段结束后 reload；
- pull 已应用成功、push 随后失败：仍需 reload，同时准确报告 push 失败；
- 无变化、审批取消、校验失败或在 apply 前失败：不 reload。

### 4.10 README 信息架构

v0.3.0 的 README 使用两段主流程：

**First use**

```text
1. Create an empty private Git repository.
2. Run /pisync.
3. Enter the repository URL when prompted.
```

**Daily use**

```text
Run /pisync on any device. It pulls remote changes first, then pushes local changes.
```

命令参考只列出 `/pisync`、`/pisync status`、`/pisync diff`。README 中不得再出现旧的 `/pisync init`、`/pisync pull`、`/pisync push` 调用示例；普通 Git 操作中的 `git pull`、`git push` 不受此限制。

## 6. 技术实现方案

### 6.1 当前实现约束

现有入口和领域逻辑有以下特征：

- `index.ts` 将无参数或未知参数路由到菜单，并分别维护 `handleInit`、`handlePull`、`handlePush`。
- `PiSyncCommands.init()` 在已初始化时只执行 fetch/pull/apply，不会执行后续 push，因此不能直接作为新的 `/pisync` 实现。
- `PiSyncCommands.pull()` 为保护本机配置，可能先 capture 和 commit，再 fetch/rebase/apply；这部分安全语义必须保留。
- UI 层 `handlePush()` 在 `preparePush()` 返回 `noop` 时直接结束；但 pull phase 可能已经生成本地 ahead commit，因此新流程不能复用这个提前返回行为。
- `pull`、`preparePush`、`executePush` 当前分别申请锁。若仅在 UI 层顺序调用，两个阶段之间存在并发窗口，reload 和错误结果也难以正确聚合。
- Package 审批可能发生在仓库已 fast-forward、但 agent 尚未完成 apply 的中间状态；审批后必须重新读取并校验状态，而不是盲目继续旧内存对象。

因此实现目标不是简单地调用 `handlePull()` 后再调用 `handlePush()`，而是在命令领域层增加一个统一编排入口。

### 6.2 目标分层

```text
index.ts
  └── handlePiSync(ctx)
        ├── cmds.run()                    # 探测生命周期状态
        ├── ctx.ui.input()                # 仅 UI 层采集 Git URL
        ├── requestPackageApproval()      # 仅 UI 层审批
        └── ctx.reload()                  # 最多一次

src/commands.ts
  └── PiSyncCommands.run(options)
        ├── inspectLifecycleState()
        ├── setupInternal()
        ├── recoverPendingInternal()
        └── syncInternal()
              ├── pullPhaseInternal()
              └── pushPhaseInternal()

src/operation-result.ts
  └── CommandResult / RunResult           # 结构化结果，不靠文案控制流程
```

UI 层只负责输入、审批、通知和 reload；状态判断、执行顺序和停止规则全部位于 `PiSyncCommands`。

### 6.3 统一领域入口

建议新增：

```ts
interface RunOptions {
  gitUrl?: string;
  packageApproval?: PackageApproval;
  onProgress?: (phase: SyncPhase, message: string) => void;
}

type RunMode = "setup" | "sync" | "recovery";
type SyncPhase = "preflight" | "pull" | "apply" | "push" | "complete";

interface RunResult extends CommandResult {
  mode: RunMode;
  phase: SyncPhase;
  details?: {
    needsGitUrl?: boolean;
    pull?: CommandResult;
    push?: CommandResult;
    approvalRequired?: string[];
  };
}

class PiSyncCommands {
  async run(options: RunOptions = {}): Promise<RunResult>;
}
```

`run()` 的控制流建议为：

```ts
async run(options = {}) {
  const lifecycle = await inspectLifecycleState();

  if (lifecycle.kind === "broken") return brokenStateResult(lifecycle);
  if (lifecycle.kind === "uninitialized") {
    if (!options.gitUrl) return needsGitUrlResult();
    return setupInternal(options);
  }

  if (lifecycle.state.pendingOperation) {
    const recovered = await recoverPendingInternal(lifecycle, options);
    if (!recovered.ok || recovered.code === "approval_required") return recovered;
  }

  return syncInternal(lifecycle, options);
}
```

首次无 URL 调用只返回结构化的 `needsGitUrl`，不在领域层读取 UI。UI 获取 URL 后再次调用 `run({ gitUrl })`。Package 审批采用相同的“返回 → 获取审批 → 重新调用并重新校验”模式。

### 6.4 生命周期状态探测

将现有 `isAlreadyInitialized()` 扩展为显式状态探测，避免把损坏状态误判成全新安装：

```ts
type LifecycleState =
  | { kind: "uninitialized" }
  | { kind: "initialized"; repoPath: string; state: SyncState }
  | { kind: "broken"; reason: string; repoPath?: string };
```

判定顺序：

1. 加载 state；
2. state 没有 `repoPath`，且默认仓库目录也不存在时，判为 `uninitialized`；
3. state 有 `repoPath` 但路径不存在，判为 `broken`；
4. 仓库缺少 `.git` 或 `pi-sync.json`，判为 `broken`；
5. 加载并校验配置成功后，判为 `initialized`；
6. 不捕获并吞掉配置错误；将可操作原因返回 UI。

该函数应成为 setup、sync、`getRepoPathSafe()` 相关分派的单一事实来源，减少状态判断分叉。

### 6.5 setup phase

`setupInternal()` 复用当前 `initFresh()` 的核心逻辑，但统一产品术语和结果类型：

- 保留 Git URL 校验、repo state 探测、clone/scaffold、初始 capture、apply、Package 审批和备份；
- 将 `initFresh`、`initAlreadyInitialized` 的职责拆开；已初始化路径不再进入 setup；
- 返回 `RunResult.mode = "setup"`；
- 对外消息使用 setup，不再使用 init；
- 移除公共 `force` 参数；内部测试辅助函数可继续显式创建 fixture，但不暴露给命令入口。

### 6.6 sync phase

`syncInternal()` 必须严格串行：

```ts
const pullResult = await pullPhaseInternal(...);
reload ||= pullResult.reload;
if (!pullResult.ok || pullResult.code === "approval_required") {
  return aggregate(pullResult, undefined, reload);
}

const pushResult = await pushPhaseInternal(...);
reload ||= pushResult.reload;
return aggregate(pullResult, pushResult, reload);
```

#### Pull phase

从现有 `pull()` 提取无锁的内部实现，保留下列顺序和保护：

1. 校验 configured branch、rebase/merge 状态和工作树；
2. 比较 agent/repo/baseline；
3. 必要时 capture 并 commit 本机变化，防止远端 apply 覆盖本机数据；
4. fetch；
5. 对本机 capture commit 执行 rebase，或执行 ff-only pull；
6. apply、Package 审批、备份和 baseline 更新；
7. 返回结构化 `CommandResult`。

pull phase 非成功时不得进入 push phase。离线 fetch 不能按“已是最新”处理。

#### Push phase

从现有 `preparePush()` 和 `executePush()` 提取无锁内部实现：

1. 重新加载 config、state、HEAD 和 worktree；
2. capture pull/apply 后产生的最终本机变化；
3. 执行 validation、Secret 扫描和 Package 计划校验；
4. 有变化时 commit → fetch → rebase → push shared/device branches → apply；
5. 没有工作树变化时，仍调用 shared/device branch 同步逻辑，确保 pull phase 生成的 ahead commit 被推送；
6. 保留 stale fingerprint 校验作为纵深防御；
7. push 失败时保留本地 commit，并在结果中携带前一阶段的 reload 需求。

最终结果码聚合规则：

- 任一阶段失败：使用失败阶段的 code；
- 需要审批：`approval_required`；
- 两阶段都无变化且没有分支需要推送：`noop`；
- 任一阶段应用、提交或推送了变化：`ok`。

### 6.7 锁与重入

目标是一次 `run()` 的 setup、recovery 或 sync 执行只持有一个顶层锁：

```text
run()
  acquire("sync")
  try { recovery/pull/push }
  finally { release() }
```

为避免嵌套死锁：

- 提取 `pullPhaseInternal`、`preparePushInternal`、`executePushInternal`，这些内部函数假设调用方已持锁；
- 若保留面向单元测试的 public phase wrapper，由 wrapper 自己申请锁，但 `run()` 不调用 wrapper；
- 等待 URL 输入或 Package 审批时不持锁；返回 UI 前释放锁，用户响应后重新进入 `run()` 并重新校验 HEAD、worktree、state 和 approval plan；
- 不跨 UI await 保存可执行的旧 `PushPreparation`。

这样既消除 pull/push 阶段间竞争，也保留审批等待期间的可用性和 stale-state 防护。

### 6.8 pending operation 恢复

将 `pushContinue()` 改为内部的 `recoverPendingInternal()`，由普通 `/pisync` 自动分派：

| pending type | 恢复策略 |
| --- | --- |
| `push-rebase-conflict` | 校验无 unmerged paths、工作树干净、最终内容通过 validation/Secret scan；推送后清空 pending |
| `apply-failed` | 重新构建 apply/package plan；成功后清空 pending，再继续 pull → push |
| 未知类型 | fail closed，保留 state 并报告升级或人工处理建议 |

恢复函数不得仅依赖 pending 字段，还必须检查当前 Git 状态。恢复成功后的正常同步应重新 fetch，不能假定冲突处理期间远端没有变化。

### 6.9 `index.ts` 路由改造

命令注册目标：

```ts
pi.registerCommand("pisync", {
  description: "Set up or sync Pi configuration via Git",
  getArgumentCompletions: getPiSyncArgumentCompletions,
  async handler(args, ctx) {
    switch (args?.trim()) {
      case "":
      case undefined:
        return handlePiSync(cmds, ctx);
      case "status":
        return handleStatus(cmds, ctx);
      case "diff":
        return handleDiff(cmds, ctx);
      default:
        return notifyInvalidArgument(args, ctx);
    }
  },
});
```

对应清理：

- `pisyncSubcommands` 只保留 `status`、`diff`；
- 删除默认菜单分派；
- 删除 `showMenu`、`getMenuChoice`、`executeMenuChoice` 和仅供菜单使用的 TUI/RPC 组件代码；
- 用一个 `handlePiSync` 替代 `handleInit`、`handlePull`、`handlePush`；
- 清理不再使用的 `SelectList`、`Input`、`getRepoSummary` 等 import/函数；
- 未知参数只通知，不执行任何领域写操作；
- UI 根据 `RunResult.code/details` 处理 URL、Package 审批、通知和一次性 reload，不通过 message 文本判断控制流。

### 6.10 通知与 reload 聚合

建议最终通知结构为：

```text
◆ pi-git-sync: Sync completed.
Pull: Applied 2 remote changes.
Push: Pushed 1 local change.
```

部分失败示例：

```text
◆ pi-git-sync: Sync incomplete.
Pull: Applied remote changes.
Push: Failed; local commit was preserved.
```

`RunResult.reload` 表示整个调用期间是否有 agent 变更。`handlePiSync` 在最终通知后只检查一次该字段。即使最终 code 是失败，只要 pull/apply 已改变 agent，仍执行一次 reload。

## 8. 测试方案

### 8.1 命令路由

- 无参数、未初始化：请求 URL 并进入 setup；取消无副作用。
- 无参数、已初始化：直接执行 sync，不打开菜单。
- `status`、`diff` 保持只读行为。
- `init`、`pull`、`push`、`push --continue` 和未知参数均不调用写操作。
- 补全列表只包含 `status`、`diff`。
- 命令 description 不再宣传旧写子命令。

### 8.2 生命周期状态

- 完全无 state/repo → uninitialized。
- 有效 state/repo/config → initialized。
- state 指向不存在目录、缺 `.git`、缺配置、配置非法 → broken 且无覆盖。
- 已有设备升级后无需重新 setup。

### 8.3 顺序与停止条件

- 用 spy/fixture 证明 pull phase 完成后才进入 push phase。
- pull `noop` 后仍执行 push phase。
- pull 创建 ahead commit、push 无工作树变化时，commit 仍到达 shared/device remote branches。
- pull 冲突、validation、Secret、Git 失败时不调用 push。
- push 失败时保留本地 commit，并保留 pull 阶段产生的 reload。
- 完全无变化返回 `noop`。

### 8.4 审批与重入

- pull apply 需要 Package 审批时暂停；批准后重新校验并完成 push。
- 拒绝审批不 push、不 reload。
- 审批等待期间 HEAD 或 worktree 改变时，重新准备而不是执行旧 preparation。
- setup 的 Package 审批路径保持可用。

### 8.5 恢复与冲突

- 旧 `push-rebase-conflict` state 可通过普通 `/pisync` 恢复。
- 冲突未解决、仍有 unmerged path 或 dirty worktree 时保持 pending。
- `apply-failed` 在问题消除后可重试并继续同步。
- 恢复后再次 fetch，处理恢复期间新增的远端提交。

### 8.6 reload

- setup 成功最多 reload 一次。
- pull 和 push 都产生 apply 时仍只 reload 一次。
- pull 已应用、push 失败时 reload 一次。
- noop、输入取消、审批拒绝和 apply 前失败不 reload。

### 8.7 E2E

至少覆盖：

1. 设备 A 首次 `/pisync` 完成 setup；
2. 设备 A 修改配置并 `/pisync`；
3. 设备 B 已初始化，存在不同本机修改；
4. 设备 B `/pisync` 先取得 A 的变化，再推送 B 的变化；
5. 设备 A 再次 `/pisync` 后两设备、shared branch、device branches 和 baseline 收敛；
6. 重复执行 `/pisync` 幂等并返回 noop。

### 8.8 文档与质量门禁

- README 命令示例扫描：`/pisync (init|pull|push)` 必须为 0；历史 docs 不参与该断言。
- TypeScript LSP/`npm run typecheck` 无错误。
- 单元、集成、E2E 和 coverage 测试全部通过。
- 删除路由和菜单后无未使用 import、死函数或旧测试名称遗漏。

## 10. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 无参数命令从“打开菜单”变为“执行写操作” | README、upgrade 和 release notes 明确提示；未知参数绝不回退执行 |
| UI 层简单串联导致阶段间竞争 | 在领域层统一编排并使用顶层锁 |
| pull 生成 commit 后被 push noop 跳过 | push phase 即使无工作树变化也同步 ahead/shared/device branches |
| Package 审批造成半完成状态 | 审批前释放锁，审批后重新加载并校验，再继续 |
| 后续 push 失败掩盖 pull 已应用的 reload | 聚合整个 run 的 reload，最终只调用一次 |
| 删除 `push --continue` 导致旧 pending 死锁 | 普通 `/pisync` 自动进入 recovery |
| 损坏 state 被误判为首次安装 | 三态 lifecycle inspector，broken 状态 fail closed |
| 旧命令 alias 长期残留 | 不注册 alias，仅返回无副作用迁移提示，并增加路由测试 |

## 11. 完成定义

v0.3.0 只有在以下条件全部满足后才算完成：

1. 新用户只用 `/pisync` 完成 setup。
2. 已初始化用户只用 `/pisync` 完成严格的 pull phase → push phase。
3. 命令注册、补全和菜单中不存在 `init`、`pull`、`push` 写子命令。
4. `status`、`diff` 保持兼容且只读。
5. pull 失败时绝不 push；pull 产生的 ahead commit 不会因 push noop 丢失。
6. Package 审批、冲突恢复、Secret 扫描、备份回滚和 device branch 保护保持有效。
7. 一次调用最多 reload 一次，且部分失败不丢失必要 reload。
8. 已有 v0.2.x state 无需重新初始化，旧 pending state 可恢复。
9. 双语 README 不再包含旧 `/pisync init|pull|push` 使用方式。
10. typecheck、单元测试、集成测试和两设备 E2E 全部通过。
