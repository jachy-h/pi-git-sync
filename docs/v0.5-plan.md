# pi-git-sync v0.5.0 架构收敛与主流程质量计划

> 状态：Draft  
> 设计基线：v0.4.2  
> 版本主题：保持现有同步语义与安全模型不变，用最小、可验证的拆分收敛编排复杂度，并让测试门禁真实覆盖用户主流程。  
> 最后更新：2026-07-29

## 1. 背景与审查结论

v0.4 已完成结构化冲突结果、四选一冲突处理、device branch 恢复锚点和 local/remote 自动解决。当前系统的基础架构方向合理：

- `inventory` / `capture` / `materialize` 分别承担三方比较、agent → repo、repo → agent；
- Git、state、backup、path safety、security、package reconciliation 已形成独立模块；
- extension UI 与领域命令入口分离；
- 当前生产模块依赖图没有循环；
- backup、atomic write、secret scan、package approval、sync lock 和 device branch 共同形成了较完整的安全边界。

本轮审查没有发现需要重写底层同步模型的结构性错误，主要问题集中在编排层、测试门禁和文档一致性。

### 1.1 当前基线

| 指标 | 当前结果 |
| --- | --- |
| 生产源码 | 20 个 TypeScript 文件，约 9271 行 |
| `src/commands.ts` | 3335 行，占生产源码约 36% |

| 全量测试 | 33 个测试文件、321 个测试通过 |

| `src/commands.ts` 覆盖率 | statements 63.27%、branches 65.28% |

关键编排函数仍然偏大：

- `pull()`：圈复杂度约 43；
- `initFresh()`：约 40；
- `applyCurrent()`：约 44；
- `preparePush()`：约 30；
- `executePush()`：约 24；
- `handlePiSync()`：约 35。

| 流程 | 行覆盖率 |

因此当前状态可概括为：**主成功路径已覆盖，主生命周期中的 setup、失败、回滚和恢复路径仍缺少足够保护；架构边界合理，但 `PiSyncCommands` 已成为 God Class。**

### 1.2 测试脚本现状

当前 `package.json` 还存在以下不一致：

1. `test:coverage` 会执行 `test/**/*.test.ts`，已经包含 E2E；`test:ci` 随后再次执行 `test:e2e`，同一组 E2E 被重复运行；
2. `test:unit` 实际执行所有测试，也包含 E2E；
3. `test:integration` 指向不存在的 `test/integration` 和 `test/contract`，因 `--passWithNoTests` 而以成功退出；
4. `test:smoke` 仍引用已删除的 `test/minimatch.test.ts`；
5. 全局 statements/lines 阈值只有 45%，即使核心编排覆盖明显回退，CI 仍可能通过。

### 1.3 文档现状

README 的 Pull Flow 仍描述“发现未捕获本地变化时阻断”，而实际 `pull()` 会先 capture、commit，再 fetch/rebase/apply。实现行为有安全理由，但文档心智模型已经过期。

## 2. 版本目标

1. 保持 `/pisync`、`/pisync status`、`/pisync diff` 的公共 API 不变；
2. 保持 config schema v2、state schema v3、device branch 和三方比较语义不变；
3. 将 `PiSyncCommands` 收敛为公共 façade、生命周期判断、锁边界和高层阶段编排；
4. 优先消除 pull/push/apply 中重复的冲突处理、锁模板和错误结果构造；
5. 用小步提取降低 `commands.ts` 的文件耦合与函数复杂度，不进行一次性重写；
6. 让测试脚本名称、执行范围和 CI 行为一致，消除空跑与重复 E2E；
7. 为首次 setup、日常同步、冲突、回滚、审批和 pending recovery 建立可追踪的主流程测试矩阵；
8. 提高覆盖率门禁，使核心编排覆盖回退可以阻断 CI；
9. 修正文档与实际 pull、测试和恢复语义的不一致。

## 3. 非目标

v0.5.0 不做以下事情：

- 不引入状态机框架、依赖注入容器、事件总线或 command bus；
- 不为每个错误码、Git 命令或冲突选项创建类；
- 不重写 inventory、capture、materialize 或 Git 算法；
- 不新增公共写子命令；
- 不改变 local/remote 冲突语义；
- 不改变 package trust、backup、secret scan 或 hard deny 策略；
- 不以追求 100% 覆盖率为目标；
- 不为了降低行数而移动代码但保留同等复杂度；
- 不在同一个提交中同时做模块拆分和同步行为变更。

## 4. 设计原则

### 4.1 先测试，后移动

所有提取都必须先由行为测试固定当前契约。重构提交不改变输出 code、state、Git 历史、reload、device branch 或错误恢复行为。

### 4.2 公共 façade 保持稳定

`PiSyncCommands` 继续是 extension 与测试可使用的领域入口。v0.5 不要求调用方感知内部模块拆分。

### 4.3 内部阶段无锁，公共入口持锁

一次 `/pisync` 只持有一个顶层锁。提取后的 phase 函数假定调用方已持锁，不自行 acquire/release；用于兼容或测试的 public wrapper 才建立自己的锁边界。

### 4.4 优先 options object，不增加 service hierarchy

提取函数参数超过 5 个时使用一个窄 options object。默认直接 import 现有底层函数，不建立 `GitService`、`StateRepository` 等只有一个实现的接口。

### 4.5 结构化结果，不用 message 控制流程

新增或提取的控制流继续使用 discriminated union、`CommandResult`、`RunResult` 和 `SyncConflictRequest`。message 只用于展示。

### 4.6 安全失败保持局部可恢复

任何提取都不得削弱：

- pull 失败后不 push；
- 未知 dirty worktree 不 hard reset；
- device branch 不自动删除；
- push 不使用 force；
- apply 前备份失败则停止；
- apply/package 失败时回滚并保留恢复信息；
- 审批等待后重新加载 state、HEAD 和 plan。

## 5. 目标模块边界

推荐目标如下：

```text
index.ts
  ├── command registration
  ├── UI input / approval / notification / reload
  └── cancellation + progress runner

src/commands.ts                    # 稳定 façade
  ├── public run/status/diff/resolveConflict
  ├── lifecycle inspection
  ├── top-level lock boundaries
  ├── phase ordering and result aggregation
  └── compatibility wrappers used by tests/internal callers

src/apply-transaction.ts           # 建议新增
  ├── no-op/state-only convergence
  ├── backup → materialize → package execution
  ├── rollback and pending apply-failed recording
  └── final state commit

src/pull-phase.ts                  # 建议新增
  ├── branch/worktree preflight
  ├── local capture before fetch
  ├── fetch + rebase/fast-forward
  └── return structured phase outcome

src/push-phase.ts                  # 建议新增
  ├── prepare/fingerprint/validation
  ├── commit + fetch + rebase
  ├── shared/device branch push
  └── return structured phase outcome

src/setup-flow.ts                  # 建议新增
  ├── Git URL and repository-state decisions
  ├── clone/scaffold
  ├── existing repository setup
  └── initial capture/apply

src/conflict-resolution.ts
  └── 保持低层冲突事务和 local/remote stage 解析

src/{inventory,capture,materialize,backup,git,state,packages,...}.ts
  └── 继续保持现有领域职责
```

这是一条迁移方向，不要求一次创建全部文件。只有当一段逻辑具备清晰输入、结构化输出和独立测试后才移动。

### 5.1 `PiSyncCommands` 最终职责

v0.5 完成后，`PiSyncCommands` 应主要回答以下问题：

1. 当前是 uninitialized、initialized 还是 broken；
2. 是否成功获得顶层操作锁；
3. setup、recovery、pull、push 的执行顺序是什么；
4. 某阶段失败后是否继续；
5. 如何聚合 `RunResult`、reload 和 conflict details；
6. extension 可以调用哪些稳定入口。

文件复制、Git subprocess、package 安装、backup/materialize 事务不应继续直接展开在 façade 中。

## 6. 技术方案指导

### 6.1 第一步：固定结果与主流程契约

重构前先补充以下黑盒测试：

```ts
// 示例，不要求使用完全相同的 helper 名称
const result = await commands.run({ gitUrl });
expect(result).toMatchObject({
  ok: true,
  mode: "setup",
  phase: "complete",
});
```

测试应尽量通过 `PiSyncCommands.run()` 或注册后的真实 `/pisync` handler，而不是直接调用未来会被移动的 private phase。

必须先固定：

- setup 成功和取消；
- broken lifecycle fail closed；
- pull → push 顺序；
- pull failure 不进入 push；
- ahead commit 即使 worktree clean 也会 push；
- package approval 重入；
- conflict request 传播；
- apply/package rollback；
- pending recovery；
- reload 聚合与重复执行 noop。

### 6.2 第二步：消除重复锁模板

当前多个 public 方法重复：

```ts
const acquired = this.orchestrationLockHeld || await this.lock.acquire(...);
if (!acquired) return failureResult(...);
try {
  // operation
} finally {
  if (!this.orchestrationLockHeld) await this.lock.release();
}
```

建议在 `PiSyncCommands` 内先增加一个私有 helper，而不是把领域结果耦合进 `SyncLock`：

```ts
private async withCommandLock<T>(
  operation: string,
  onBusy: () => T,
  run: () => Promise<T>,
): Promise<T> {
  if (this.orchestrationLockHeld) return run();
  if (!(await this.lock.acquire(operation, 5000))) return onBusy();
  try {
    return await run();
  } finally {
    await this.lock.release();
  }
}
```

约束：

- helper 只管理 ownership，不解释 pull/push/apply 语义；
- 顶层 `run()` 持锁后调用 lock-free internal phase；
- UI 输入和 package approval 等待期间不得持锁；
- 不把 `orchestrationLockHeld` 暴露到新模块。

### 6.3 第三步：先提取重复冲突协调 helper

`pull()`、`preparePush()` 和 `applyCurrent()` 多次重复以下序列：

```text
preserveConflictOnDeviceBranch
  → fast-forward if possible
  → mergeDeviceBranchIntoShared if clean
  → createSyncConflictRequest otherwise
  → apply resolved result
```

先在 `commands.ts` 内提取一个 private discriminated-union helper，确认输入输出稳定后再决定是否移动文件：

```ts
type ConflictCoordinationResult =
  | { kind: "resolved"; message: string }
  | { kind: "needs_user"; conflict: SyncConflictRequest; message: string };
```

不要创建 `ConflictCoordinator` 基类或 strategy registry。现有 `src/conflict-resolution.ts` 继续负责低层 Git 冲突事务；高层 device/shared branch 协调仍属于同步编排。

### 6.4 第四步：提取 apply transaction

`applyCurrent()` 可先分为两段：

1. **协调段**：`planMaterialize`、冲突判断、package approval 判断；
2. **事务段**：no-op/state convergence、backup、materialize、package execution、rollback、state commit。

建议新增：

```ts
interface ApplyTransactionOptions {
  agentDir: string;
  commit: string;
  branch: string;
  reason: string;
  state: SyncState;
  plan: MaterializePlan;
  packagePlan: PackagePlan;
  packageApproval?: PackageApproval;
}

async function executeApplyTransaction(
  options: ApplyTransactionOptions,
): Promise<CommandResult>;
```

事务函数只接受已经通过 conflict/approval 检查的 plan，不回调 `PiSyncCommands`，从而避免循环依赖。它必须保持以下提交点：

```text
backup 成功
  → materialize 成功
  → package 成功
  → state 最终提交
```

中间任何失败都不得写入“完成状态”。package 失败继续记录 `apply-failed` pending operation。

### 6.5 第五步：提取 pull phase

将 `pull()` 按顺序拆成窄函数，先在原文件提取，再移动到 `src/pull-phase.ts`：

```text
inspectPullRepository
captureLocalChangesBeforePull
fetchAndIntegrateRemote
applyPulledHead
```

推荐的 phase 参数：

```ts
interface PullPhaseOptions {
  agentDir: string;
  repoPath: string;
  config: PiSyncConfig;
  state: SyncState;
  packageApproval?: PackageApproval;
  signal?: AbortSignal;
  onProgress?: RunOptions["onProgress"];
  onGitCommandStart?: RunOptions["onGitCommandStart"];
}
```

如果 phase 发现内容冲突，应返回结构化 outcome 给 façade 协调，不直接读取 UI，也不生成新的公共命令。

### 6.6 第六步：提取 push phase

保留 prepare/execute 两段语义，因为 fingerprint 是有价值的 stale-operation guard；但将其限制在同一个模块：

```ts
preparePushPhase(options): Promise<PushPreparation>
executePushPhase(options, preparation): Promise<CommandResult>
```

必须继续验证：

- preparation 的 repo HEAD；
- agent/repo worktree fingerprint；
- configured branch；
- fetch 后的 remote ref；
- rebase conflict；
- shared/device branch 都被同步；
- push 成功、apply 失败时不能声称 push 失败。

不要为 `ready`、`noop`、`blocked` 创建类；保留 discriminated union。

### 6.7 第七步：最后提取 setup flow

setup 当前覆盖最低，应在测试补齐后最后移动。拆分建议：

```text
validateSetupRequest
inspectExistingDefaultRepository
cloneOrScaffoldRepository
initializeLocalState
applyInitialConfiguration
```

必须覆盖两种真实用户场景：

1. 空远端：当前设备内容成为初始配置；
2. 已有远端：新设备 clone 后应用远端配置。

`init()` 可以继续作为内部兼容 wrapper，但新的主流程测试应优先调用 `run({ gitUrl })`。

### 6.8 `index.ts` 的最小收敛

`handlePiSync()` 的 cancellation、watchdog、elapsed progress 和 retry 逻辑有真实产品需求，不应仅因复杂度高而删除。v0.5 只建议提取一个 UI-agnostic runner：

```ts
interface OperationRunnerOptions {
  signal: AbortSignal;
  onProgress: RunOptions["onProgress"];
  onGitCommandStart: RunOptions["onGitCommandStart"];
}
```

边界要求：

- runner 只负责 timeout/cancel/progress；
- URL 输入、package approval、conflict choice 和 reload 留在 `handlePiSync()`；
- 不让 runner 感知 Git branch、state 或 package plan；
- 不改变 Escape、60 秒 watchdog 和命令级 timeout 行为。

## 7. 测试体系方案

### 7.1 主流程测试矩阵

| 主流程 | 当前状态 | v0.5 要求 |
| --- | --- | --- |
| 未初始化 → 请求 URL | 已覆盖 | 保留 |
| `run({ gitUrl })` 完整首次 setup | 不充分 | 增加真实 Git 集成测试 |
| 已有远端的新设备 onboarding | 部分由 fixture 手工建立 | 增加通过 setup/run 的测试 |
| pull → push 日常同步 | 已覆盖 | 保留并减少对内部实现断言 |
| 两设备 round-trip + noop | 已覆盖 E2E | 保留 |
| 双边冲突 + local/remote | 已覆盖 E2E | 保留 |
| fetch 失败停止 push | 已覆盖 | 保留 |
| apply 文件写入失败 → rollback | 底层覆盖，主编排不足 | 增加 run/apply 集成测试 |
| package 失败 → rollback + pending | 已覆盖部分 | 增加普通 `/pisync` 恢复测试 |
| stale push preparation | 覆盖不足 | 增加 HEAD 和 worktree 两种变化 |
| 顶层锁竞争 | lock 单元覆盖，run 不足 | 增加 run fail-closed 测试 |
| broken lifecycle | 已覆盖部分 | 补齐缺 `.git`、缺 config、非法 config |
| timeout / Escape | extension 层已覆盖 | 保留，降低时序脆弱性 |

### 7.2 E2E 层级

保留少量高价值 E2E，不把所有错误注入都放入 E2E：

1. extension `/pisync` 首次 setup；
2. 两设备完整 round-trip；
3. 双边冲突保留 device branch；
4. use local / use remote 最终收敛；
5. 重复 `/pisync` 返回 noop。

Git 命令失败、backup/materialize/package rollback 使用临时仓库和测试 helper 的 integration test 验证，避免 E2E 运行时间失控。

### 7.3 测试脚本收敛

建议先不移动全部测试文件，只修正脚本的真实语义：

```jsonc
{
  "test": "vitest run",
  "test:core": "vitest run --exclude test/e2e/**",
  "test:e2e": "vitest run test/e2e --no-file-parallelism",
  "test:coverage": "vitest run --coverage --exclude test/e2e/**",
  "test:smoke": "vitest run test/glob.test.ts test/ui.test.ts",
  "test:ci": "npm run typecheck && npm run test:coverage && npm run test:e2e"
}
```

处理原则：

- 删除空跑的 `test:integration`，或在真正建立对应目录后再恢复；
- 删除已不存在的 `test/minimatch.test.ts` 引用；
- `test:unit` 若保留，必须明确是否只是 `test:core` 的兼容 alias；
- coverage 排除 E2E 后先记录新基线，再调整阈值；
- `npm test` 仍可作为开发者的一键全量入口。

### 7.4 覆盖率门禁

不建议直接把全局阈值提高到当前观测值，否则轻微环境差异会造成无意义失败。分两步：

#### 第一步：建立不回退基线

- 对排除 E2E 后的 core suite 重新记录 statements/branches/functions/lines；
- 将全局阈值设置为低于稳定基线 2–3 个百分点；
- statements/lines 不再维持 45% 的宽松值；
- functions 阈值应接近当前 90%+ 的真实水平。

#### 第二步：保护关键文件

优先保护：

- `index.ts`；
- `src/commands.ts`；
- `src/apply-transaction.ts`；
- `src/pull-phase.ts`；
- `src/push-phase.ts`；
- `src/setup-flow.ts`；
- `src/conflict-resolution.ts`。

若当前 Vitest 版本支持 glob/per-file thresholds，直接配置；否则增加一个小型 `scripts/check-coverage.mjs` 读取 `coverage-summary.json`。脚本只比较数值，不引入新的测试框架。

目标不是用覆盖率替代行为断言，而是防止复杂编排重新退回到低覆盖状态。

## 8. 文档方案

v0.5 需要同步更新：

- `README.md`：Pull Flow 改为“先保护并 capture 本地变化，再 fetch/rebase/fast-forward/apply”；
- `README.zh.md`：保持同义；
- `docs/architecture.md`：更新 façade + phase + transaction 模块图；
- `docs/upgrade.md`：若无用户可见行为变化，只记录内部架构和测试门禁，无需迁移步骤；
- `CHANGELOG.md`：记录测试脚本语义变化、架构拆分和新增恢复测试。

文档不得承诺实现中不存在的 `test/integration`、阻断式 pull 或独立公共 pull/push 命令。

## 9. 分阶段实施

### Phase 0：基线与计划

1. 固化当前类型、测试、coverage 和依赖图结果；
2. 记录 `commands.ts` 的高复杂度和低覆盖区域；
3. 建立 v0.5 plan/progress；
4. 不修改生产行为。

### Phase 1：测试脚本与主流程契约

1. 修正 `test:unit/core/integration/e2e/smoke/coverage/ci` 语义；
2. 消除 E2E 重复执行；
3. 增加 setup、onboarding、rollback/recovery、lock、stale preparation 测试；
4. 建立新的 coverage 基线和门禁。

### Phase 2：低风险去重

1. 提取 lock wrapper；
2. 提取统一 failure/result helper，但不隐藏错误码；
3. 提取重复 conflict coordination private helper；
4. 验证行为和 coverage 不回退。

### Phase 3：apply transaction 拆分

1. 将 non-conflict apply 事务移到 `src/apply-transaction.ts`；
2. 保留 plan/conflict/approval 协调；
3. 覆盖 backup/materialize/package/state 各提交点和 rollback；
4. 确保 pending recovery 仍通过普通 `/pisync` 工作。

### Phase 4：pull / push phase 拆分

1. 提取 `src/pull-phase.ts`；
2. 提取 `src/push-phase.ts`；
3. 保留 structured conflict outcome、fingerprint 和 device branch 语义；
4. 删除迁移后确认无用的 façade private helper/export；
5. 执行两设备 E2E。

### Phase 5：setup 与 extension runner 收敛

1. 补齐 setup 测试后提取 `src/setup-flow.ts`；
2. 视复杂度收益提取 operation runner；
3. `commands.ts` 只保留 façade、lifecycle、lock 和 phase ordering；
4. 不改变公共命令和用户文案，除非用于修正文档不一致。

### Phase 6：文档与发布

1. 更新 README、architecture、upgrade、CHANGELOG；
2. 执行 typecheck、core coverage、E2E、audit 和 package dry-run；
3. 执行临时远端两设备人工 smoke test；
4. 发布 v0.5.0。

## 10. 建议提交边界

为降低回归定位成本，建议每个 commit 只做一类改变：

1. `test: align npm test scripts with real suites`
2. `test: cover setup and recovery lifecycle`
3. `refactor: centralize command lock ownership`
4. `refactor: deduplicate conflict coordination`
5. `refactor: extract apply transaction`
6. `refactor: extract pull phase`
7. `refactor: extract push phase`
8. `refactor: extract setup flow`
9. `docs: align sync model and v0.5 architecture`

每个 refactor commit 前后必须独立通过相关测试。不要把文件移动、行为修复和覆盖阈值调整放在同一提交中。

## 11. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 拆分后出现循环依赖 | phase 只依赖底层模块和结构化类型；`commands.ts` 单向调用 phase，phase 不 import façade |
| lock ownership 在 public/internal wrapper 间混乱 | 明确 public 持锁、internal 无锁；增加 run 和 wrapper 并发测试 |
| conflict helper 过度抽象 | 先做 private discriminated-union helper，有第二个稳定消费者后再移动 |
| apply 拆分破坏事务提交点 | 为 backup、materialize、package、state 四个阶段建立失败注入测试 |
| 测试仅覆盖 private 实现 | 主契约优先通过 `run()` 和 extension handler；phase 测试只覆盖复杂矩阵 |
| coverage 排除 E2E 后骤降 | 先记录基线，再设置阈值；不在同一提交同时排除和大幅提高门槛 |
| 重构改变错误文案导致脆弱测试 | 断言 code/details/state/Git 结果；仅 UI snapshot 测试固定文案 |
| 新模块过多增加导航成本 | 只创建四个有明确事务或阶段边界的模块，不为小 helper 建文件 |
| CI 时间继续增长 | core coverage 与 E2E 分离；错误矩阵放 integration，E2E 只保留跨设备主流程 |
| 文档再次漂移 | README 流程测试/扫描纳入 CI，历史 plan 不追溯修改 |

## 12. 质量目标

v0.5 以趋势目标而不是机械行数为唯一标准：

- `commands.ts` 不再包含完整 setup、pull、push、apply 事务实现；
- 建议将 `commands.ts` 收敛到约 1800 行以内，但不为达标制造无意义 wrapper；
- 新增或改写的 orchestrator 函数圈复杂度建议不超过 20；
- `commands.ts` statements/branches 覆盖率不得低于 v0.5 新基线；
- setup、pull、push、apply、recovery 每条主生命周期至少有一个成功和一个失败契约测试；
- 生产依赖图继续保持无循环；
- typecheck 和 LSP blocking errors 为 0；
- CI 中不存在“0 tests 但成功”的命名测试阶段；
- E2E 在 `test:ci` 中只执行一次。
