# pi-git-sync v0.7 工具体验与可控同步计划

> 状态：提案
> 目标版本：v0.7.0
> 依据：v0.6.3 产品与工程审查

## 1. 背景

pi-git-sync 已具备三方比较、冲突阻断、备份/回滚、路径安全、敏感信息扫描、package 审批和双设备测试等安全基础。v0.7 不改变这些安全边界，而是让用户在同步前理解影响、在冲突时做出可逆选择、在失败后能快速恢复。

当前统一命令 `/pisync` 仍把较多关键决策压缩在一次运行中：用户需先运行 `/pisync diff` 才能预览影响；冲突以全量选择为主；`status` 偏向 Git 诊断；首次设置依赖用户自行准备仓库、URL 与凭据。

## 2. 版本目标

1. 将同步从“安全但黑盒”变为“安全、可预览、可确认、可追溯”。
2. 在不降低自动化程度的前提下，为写入、删除、package 变更和冲突提供明确决策点。
3. 让非 Git 熟练用户可以理解当前状态、下一步操作和恢复路径。
4. 收敛高复杂度编排边界，保持覆盖率和跨平台质量门禁。

## 3. 非目标

- 不改变 `pi-sync.json` schema v2、state schema v3、默认同步范围或 hard deny 安全规则。
- 不引入云端账号、遥测上传或非 Git 的同步后端。
- 不在 v0.7 实现完整的逐行三方合并编辑器。
- 不移除现有 `/pisync`、`/pisync status`、`/pisync diff` 工作流。

## 4. 优先优化项

### P0：同步计划确认（预览、确认、执行）

**问题**：`/pisync` 会执行 pull、push、apply 和可能的 package 处理；用户需要额外执行 `/pisync diff` 才能理解本次影响。

**方案**：在发生本机文件写入/删除、Git push 或 package 变更前生成统一的同步计划，并在 TUI 中确认。

计划至少包括：

- 本机与远端文件的新增、更新、删除数量和关键路径；
- 将安装、更新或移除的 packages，以及其 source；
- 远端领先、分支异常、敏感信息扫描和冲突阻断状态；
- 预计下一步：安全执行、需先处理冲突、需审批 package 或无法执行的原因。

交互提供：`继续同步`、`取消`；完整计划在确认框中展开，已有 `/pisync diff` 保持只读详情入口。后续版本可评估“记住此策略并自动执行”，但 v0.7 默认始终在高影响操作前确认。

**验收标准**：

- 用户无需先运行 `/pisync diff` 也能在写入前了解影响；
- 取消不改变 agent、repo 工作树、state 或 package；
- 无 UI 环境保持现有 fail-safe / 文本提示行为；
- 计划生成与实际执行使用同一份稳定 fingerprint，执行前重新校验，避免预览过期。

### P0：文件级冲突决策与差异摘要

**问题**：现有冲突交互以“全部使用本机 / 全部使用远端 / Agent 处理”为主，用户难以针对不同文件作出选择。

**方案**：将冲突流程扩展为文件清单和摘要优先：

- 展示每个冲突路径、变更类型、文件类别和可用恢复分支；
- 为每个路径提供不含文件内容的变更类型摘要；原始内容保持交由 Agent 或手动合并处理，避免在 TUI 中泄露敏感配置；
- 支持逐文件选择本机、远端或交给 Agent；
- 执行前汇总最终选择，执行后回显处理结果与恢复路径。

**验收标准**：

- 一次冲突可对不同路径采用不同来源；
- 仍保留当前设备恢复分支，且不会 force push；
- 冲突清单不读取或泄露文件内容；二进制、超大文件和敏感配置可安全转交 Agent 或手动合并；
- 冲突选择、取消、过期 ref、package 审批和 apply 失败均有测试覆盖。

### P1：状态面板与下一步行动

**问题**：`/pisync status` 输出了 branch、commit、ahead/behind 等诊断信息，但用户首先需要知道是否安全、是否需要操作以及应该做什么。

**方案**：将状态输出重构为分层面板：

1. 顶层健康状态：`已同步`、`有本机改动`、`有远端更新`、`需要处理冲突`、`需要恢复`；
2. 明确的下一步动作：`运行 /pisync`、`查看详情`、`解决冲突` 或 `检查认证`；
3. 上次成功同步时间、当前设备、耗时和影响摘要；
4. Git branch、commit、ahead/behind、原始路径等进入“详细诊断”区。

**验收标准**：

- 无 Git 背景的用户可仅阅读顶层区域完成下一步判断；
- 现有诊断信息仍可获取；
- pending operation、锁占用、无远端、认证失败和冲突均有可执行提示。

### P1：首次设置预检与恢复引导

**问题**：用户需要自行准备空私有仓库、URL 和 Git 凭据；错误多在 clone/连接失败后返回。

**方案**：在 clone 前增加可解释的设置预检：

- Git 可用性、URL 格式、网络连通性、SSH/HTTPS 认证和远端写权限；
- 检测仓库为空、已有有效 pi-sync 配置或无效仓库，并给出对应方案；
- 提供可复制的修复命令及“不破坏现有本地仓库”的恢复路径；
- 明确说明仓库应为私有仓库以及不能同步的内容。

**验收标准**：

- 每个失败项包含原因、影响、下一步和可复制命令；
- 不因预检失败创建半成品 repo 或写 state；
- SSH、HTTPS、无权限、无网络、非空无效仓库均有集成测试。

### P1：同步范围管理入口

**问题**：同步范围由 `pi-sync.json` 管理，但普通用户需要手工编辑配置才能了解或修改范围。

**方案**：增加只修改 manifest 的配置入口（命令名称待 UX 验证），支持：

- 按 `Extensions`、`Skills`、`Prompts`、`Themes`、`settings.json` 等类别查看范围；
- 查看某路径被同步、排除或 hard deny 的原因；
- 修改前预览新增/停止管理的文件；
- 对 `delete` 策略和 secrets scan 使用明确说明及二次确认。

**验收标准**：

- 不能通过 UI 覆盖 hard deny；
- 修改生成格式稳定、可审查的 `pi-sync.json`；
- 不会自动捕获、删除或应用文件，必须由后续同步计划确认。

### P2：操作历史、性能反馈与恢复入口

**问题**：当前有进度、取消和 watchdog，但低频使用时难以追溯上次操作、失败阶段和恢复动作。

**方案**：在本机 state 中保存有限、无敏感内容的同步历史：开始/结束时间、阶段、耗时、文件计数、package 计数、结果码及恢复建议。

**验收标准**：

- `/pisync status` 可展示最近一次成功和失败操作；
- 不记录文件内容、URL 凭据、token 或敏感扫描命中内容；
- 支持从失败状态跳转至正确的重试/恢复指导；
- 大仓库或 package 操作可显示阶段耗时，帮助识别超时原因。

### P2：发布信息与文档一致性

**问题**：当前 package、CHANGELOG、源码注释和架构文档的版本标识存在不一致风险。

**方案**：在发布前校验 `package.json`、CHANGELOG、README、架构文档和入口注释中的版本、公开命令和 schema 描述。

**验收标准**：

- 发布脚本在版本信息不一致时阻断；
- CHANGELOG 记录实际发布版本和日期；
- README 的快速开始、恢复指南和命令参考与实现一致。

## 5. 工程收敛与质量目标

### 5.1 编排边界

继续拆分 `src/orchestration/commands.ts`：

- lifecycle / lock；
- 同步计划与 fingerprint；
- 状态查询；
- 冲突协调；
- 恢复和结果映射。

保持 flows 不反向依赖命令 façade，避免扩张 `system`、`sync`、`orchestration` 与 `extension` 间的循环依赖。

### 5.2 测试与 CI

- 修复当前 `src/orchestration/commands.ts` 函数覆盖率 88.73% 低于 89% 阈值的问题；
- `npm run test:ci` 必须完整通过，确保 E2E 阶段不会因 coverage gate 被跳过；
- 为同步计划取消、过期 fingerprint、逐文件冲突选择、设置预检和历史脱敏增加单元/集成测试；
- 保持 Linux 完整 CI，以及 macOS / Windows smoke；补充涉及路径、shell、Git 认证提示的跨平台场景。

## 6. 分阶段计划

### Phase 0：基线与体验规格

- 修复覆盖率门禁，建立通过的 `npm run test:ci` 基线；
- 完成同步计划、状态面板和冲突选择的文案与交互稿；
- 定义计划 fingerprint、历史数据脱敏和无 UI 降级契约。

### Phase 1：只读可见性

- 实现新的状态面板和同步计划数据模型；
- 让 `/pisync diff` 复用计划摘要；
- 实现首次设置预检的只读诊断和行动提示。

### Phase 2：计划确认与安全执行

- 在写入、删除、push、package 变更前接入确认；
- 执行前验证 fingerprint；
- 完成取消、超时、无 UI 和 stale plan 覆盖。

### Phase 3：冲突与范围管理

- 实现文件级冲突清单、摘要、选择和结果回显；
- 实现 manifest 范围查看/修改入口及影响预览；
- 完成与 Agent handoff、package 审批和恢复分支的兼容。

### Phase 4：历史、文档与发布

- 保存脱敏操作历史并接入 status；
- 增加发布一致性校验；
- 更新 README、中文文档、架构文档、升级指南和 CHANGELOG；
- 运行完整 CI、`npm pack --dry-run` 和跨平台 smoke。

## 7. 完成定义

v0.7 发布前必须满足：

- 高影响同步在 TUI 中可预览、可取消、可确认；
- 冲突可按文件理解和决策，所有路径仍具备恢复方案；
- 状态页明确给出健康状态与下一步，而不仅是 Git 原始数据；
- 首次设置和失败恢复有可操作指引；
- 同步范围修改不会绕过安全规则；
- `npm run test:ci`、跨平台 smoke、package dry-run 全部通过；
- 版本、命令、schema 与文档一致。
