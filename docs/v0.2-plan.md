# pi-git-sync v0.2 核心问题修复计划

> 状态：Draft  
> 目标版本：`0.2.0`  
> 适用范围：从 `0.1.x` 升级到 `0.2.0`  
> 核心原则：先保证同步状态正确和文件边界安全，再改善体验；任何失败都不能伪装成成功。

## 1. 背景

当前 `0.1.x` 已具备三方比较、capture、push/pull、备份、secret scan
和 package reconciliation，但现有测试通过并不代表核心链路可靠。正常 push
后可能没有更新同步基线，`capture → push` 交互无法完成；配置仓库的 symlink
可越过仓库边界，远端 package 也可能在无确认时触发安装和加载。

`v0.2.0` 是一次正确性与安全边界修复版本，不新增大规模同步能力。所有修复都必须由失败复现测试驱动，并补齐两设备 E2E。

## 2. 目标

1. 保证每次成功的 push、pull、apply、init 都生成准确且收敛的同步基线。
2. 保证 `/pisync push` 的捕获阶段可安全重试，取消确认后仍可再次推送。
3. 保证任何同步读写都不能越过 agent 目录或配置仓库目录。
4. 阻止未经用户批准的远端 package 安装和代码加载。
5. 让 `pi-sync.json.branch` 成为真实生效的单一分支配置。
6. 统一 Git 错误语义，禁止把失败解释为“已拉取”或“成功”。
7. 修正 bootstrap、备份和依赖问题，并建立 `v0.2` 发布门禁。

## 3. 非目标

- 不实现多分支同时同步。
- 不实现自动合并双边内容冲突。
- 不实现云端密钥管理或 Git commit 签名基础设施。
- 不自动卸载本机额外 package。
- 不借本版本重写 TUI 或替换 Git。
- 不以清理所有 lint/复杂度警告作为发布条件；只处理影响本计划的代码。

## 5. CORE-01：同步基线收敛

### 5.1 根因

`applyCurrent()` 将“是否需要文件 I/O”和“是否需要提交同步状态”混为一件事：

- `plan.toWrite` 和 `plan.toDelete` 为空时提前返回；
- `converged` 表示两边内容一致，但不会触发写入，因此不会更新 baseline；
- 新 baseline 只包含 `result.written`；
- `{ ...state.files, ...newBaseline }` 会保留已经删除的旧条目；
- `lastSyncedCommit` 也会因提前返回保持旧值。

### 5.2 修复方案

将“文件变更计划”和“成功后的状态快照”分离。

扩展 `MaterializePlan`：

```ts
interface MaterializePlan {
  toWrite: MaterializeWrite[];
  toDelete: string[];
  conflicts: FileComparison[];
  validationErrors: ValidationError[];
  nextBaseline: Record<string, BaselineEntry>;
  hasStateChanges: boolean;
  blocked: boolean;
}
```

`nextBaseline` 按最终预期状态构建，而不是按实际写入列表增量合并：

- `no_change`、`converged`、`remote_only`、`remote_created`：
  成功后以 repo 文件的 hash/mode 进入 baseline；
- `remote_deleted`、`both_deleted`：成功后从 baseline 移除；
- 冲突项：不生成成功 baseline，整个计划 blocked；
- hard deny 和不在 include 中的文件：永不进入 baseline。

### 5.3 实现方案

1. 在 `src/materialize.ts` 新增 `buildNextBaseline(inventory, config)`。
2. `planMaterialize()` 同时返回文件操作和完整 `nextBaseline`。
3. `applyCurrent()` 删除“无文件操作直接返回且不更新 state”的逻辑：
   - 无文件变更且状态完全一致：返回真正的 no-op；
   - 无文件变更但 commit/baseline 需要收敛：只原子更新 state，`reload: false`；
   - 有文件变更：备份、执行、校验结果，然后用 `nextBaseline` **替换** `state.files`。
4. 只有以下全部成功后才能更新同步完成状态：
   - 文件写入/删除成功；
   - 必要的 package 审批与 reconcile 成功；
   - state 原子保存成功。
5. state 保存失败时返回明确的 partial failure，并保留可恢复信息；不得返回“Pushed successfully”。
6. `lastSyncedCommit` 必须等于本次已应用的 repo HEAD。
7. `lastSyncedAt` 只在完成状态提交后更新。

### 5.4 兼容与自修复

将 state schema 升级到 v3，并增加迁移：

```ts
interface SyncStateV3 {
  schemaVersion: 3;
  repoPath: string;
  branch: string;
  lastSyncedCommit: string | null;
  lastSyncedAt: string | null;
  files: Record<string, BaselineEntry>;
  pendingOperation: PendingOperation | null;
  lastBackup: string | null;
}
```

从 v2 迁移时执行安全收敛：

- local 与 repo hash 相同：可安全将该 hash 写入 baseline；
- local 与 repo 都不存在：删除旧 baseline；
- local 与 repo 不同：保留现状并报告冲突，不猜测哪一侧正确；
- 迁移前备份旧 state。

### 5.5 验收标准

- 正常 push 后 baseline hash 与 repo/agent 相同；
- `lastSyncedCommit` 等于 push 后 HEAD；
- 随后的另一设备更新可正常 pull，不出现伪双边冲突；
- 删除同步后对应 baseline 条目不存在；
- 重复 apply/pull/push 为真正 no-op，不创建无意义备份或 reload。

## 6. CORE-02：重构 push 准备与执行流程

### 6.1 根因

`index.ts` 通过解析人类可读字符串控制流程：

```ts
if (captureOutput.includes("blocked") || captureOutput.includes("No changes")) {
  return;
}
```

同时 UI 先调用 `capture()`，确认后 `push()` 又执行一次 capture。由此产生：

- 捕获阶段后 push 无法继续；
- 取消确认后 repo 已 dirty，下一次 push 无法继续；
- 两次 capture 之间存在竞态；
- validation 使用的文件列表可能来自 capture 前的 Git status；
- 文案变化会改变控制流。

### 6.2 修复方案

引入结构化的两阶段 push：

```ts
interface PushPreparation {
  kind: "ready" | "noop" | "blocked";
  capture: CaptureResult;
  changedFiles: string[];
  diff: string;
  repoHead: string;
  worktreeFingerprint: string;
  message?: string;
}

preparePush(repoPath?): Promise<PushPreparation>
executePush(preparation: PushPreparation, options?): Promise<CommandResult>
```

行为规则：

1. `preparePush()` 可 capture 新变更，也必须识别 repo 中已经存在的待提交变更。
2. “本次没有新 capture”不等于“没有可 push 内容”。
3. UI 只根据 `kind` 判断，不解析 message。
4. 用户取消后保留 repo 工作树；下一次调用可以继续展示并推送相同 diff。
5. 确认后重新获取锁并校验 HEAD/worktree fingerprint：
   - 未变化：继续；
   - 已变化：停止并要求重新确认，不静默使用旧 diff。
6. validation 和 secret scan 必须针对 **capture 后** 的完整待提交文件集。
7. `PiSyncCommands.push()` 保留为可编程入口，但内部复用相同 preparation/execute 流程。

### 6.3 结构化命令结果

统一命令返回值，逐步移除 `message.includes(...)`：

```ts
type ResultCode =
  | "ok"
  | "noop"
  | "blocked_conflict"
  | "blocked_validation"
  | "blocked_secret"
  | "approval_required"
  | "git_failed"
  | "partial_failure";

interface CommandResult {
  ok: boolean;
  code: ResultCode;
  message: string;
  reload: boolean;
  details?: unknown;
}
```

### 6.4 验收标准

以下流程都必须可用：

```text
修改 agent → /pisync push → 确认 → 成功
修改 agent → /pisync push → 确认 → 成功
修改 agent → /pisync push → 取消 → /pisync push → 确认 → 成功
repo 已 dirty → /pisync push → 展示已有 diff → 成功
```

## 7. SEC-01：仓库与 agent 路径边界

### 7.1 根因

当前配置只拒绝绝对路径和 `..`。如果 `repo/<root>` 自身是 symlink，
`readdir()`、`readFile()`、`writeFile()` 和 `unlink()` 会跟随到仓库外部。

### 7.2 修复方案

新增统一路径安全模块，例如 `src/path-safety.ts`：

```ts
resolveRepoSyncRoot(repoPath, root, intent): Promise<SafeRoot>
resolveWithinRoot(root, relativePath, intent): Promise<string>
assertNoSymlinkComponents(root, relativePath): Promise<void>
```

规则：

1. 对 repoPath、sync root 和每一级已存在路径执行 `lstat`；root 或中间组件是 symlink 时拒绝。
2. 使用 `realpath` 验证最终已存在路径仍位于可信 root 内。
3. 不存在的路径只能在已经验证安全的父目录下创建。
4. repo 中的文件 symlink、目录 symlink、dangling symlink 都作为阻断错误报告，不再静默跳过。
5. agent 写入、删除、backup 和 restore 使用同一套边界检查。
6. symlink 检查尽量靠近实际 I/O；关键写入采用临时文件、`O_NOFOLLOW`（平台支持时）和 rename。

所有以下模块必须通过安全 resolver 获取路径：

- `inventory.ts`
- `capture.ts`
- `materialize.ts`
- `backup.ts`
- `validate.ts`
- `packages.ts`
- `commands.ts` 中的 secret scan

### 7.3 验收标准

- `sync -> /tmp/outside` 时 capture/apply 在任何写入前失败；
- 相对、绝对、dangling 和循环 symlink 均被拒绝；
- repo 外文件内容和 mtime 不发生变化；
- Windows 无 symlink 权限时，路径逻辑测试仍运行，真实 symlink fixture 可带明确 skip 原因；

## 8. SEC-02：Package 信任与审批

### 8.1 根因

远端 `settings.json` 的 `packages[]` 可直接进入 `pi install`。当前“可移植性校验”
不是安全策略；字符串 npm/git/HTTPS 来源会通过，`{ source }` 对象也没有完整
类型和来源验证。

### 8.2 修复方案

将 package 处理拆为“解析、计划、审批、执行”四步：

```ts
parsePackageDeclarations(settings): PackageDeclaration[]
planPackageChanges(local, remote, trustStore): PackagePlan
approvePackagePlan(plan, ui): PackageApproval
executePackagePlan(plan, approval): ReconcileResult
```

默认策略：

- 未变化、已安装且已信任的 source：不提示；
- 新增或 source 变化：`approval_required`；
- 非交互环境：默认拒绝自动安装，并输出手动命令；
- 本地绝对/相对路径、`file:`、含控制字符的 source：拒绝；
- npm source 建议要求精确版本；git source 建议要求 commit SHA；
- `{ source }` 与字符串声明走完全相同的 schema 和安全校验。

本地 trust store：

```text
~/.pi/agent/.pi-sync/package-trust.json
```

记录规范化 source 与用户批准的完整标识；该文件继续受 hard deny 保护，不参与同步。

### 8.3 执行时序

package 审批必须发生在写入可能触发 package 加载的 `settings.json` 之前：

```text
plan materialize
→ 提取 settings package diff
→ 请求/验证审批
→ 创建备份
→ 写入配置
→ 执行 package reconcile
→ 保存完成状态
→ reload
```

如果安装失败：

- 不标记完整同步成功；
- 尝试恢复 settings 和已修改文件；
- 记录结构化 pending operation，允许安全重试；
- 不自动 reload 到半完成状态。

### 8.4 验收标准

- 恶意远端新增 package 时，pull 不执行 `pi install`，先返回审批请求；
- 取消审批时 agent settings、state 和已安装 package 不变；
- source 变化需要重新审批；
- object source 不可绕过校验；
- argv 继续使用 `execFile` 数组，不使用 shell；
- 批准、安装、state、reload 的顺序有自动化断言。

## 9. CORE-03：单一分支语义

### 9.1 修复方案

1. `config.branch` 是同步操作的唯一目标分支。
2. 使用 `git check-ref-format --branch` 验证分支名。
3. 每个网络命令前验证：
   - 当前分支等于 `config.branch`；
   - 工作树状态允许切换；
   - `origin/<config.branch>` 是否存在。
4. dirty/rebase/merge 状态下不自动切换分支，只给出修复指引。
5. init/clone 明确 checkout 配置分支；新仓库 scaffold 使用配置的目标分支。
6. fetch/pull/push/rebase、ahead/behind 和 status 都使用 `config.branch`。
7. state 中的 branch 在成功同步后与 config 保持一致。

### 9.2 验收标准

- `branch: "sync-config"` 的 init、push、pull 和 rebase 全部只操作该分支；
- 当前分支错误时命令明确失败，不误操作 `main`；
- 远端目标分支缺失时首推和普通同步行为可区分；
- bootstrap 不再硬编码 `main`。

## 10. CORE-04：Git 错误模型

### 10.1 修复方案

将当前始终 resolve 的 `gitExec()` 改为严格语义：

```ts
class GitCommandError extends Error {
  args: string[];
  cwd: string;
  exitCode: number | null;
  stdout: string;
  stderr: string;
  timedOut: boolean;
}

gitExec(...): Promise<GitCommandOutput> // 非零退出时 throw
gitProbe(...): Promise<GitCommandOutput & { ok: boolean }> // 仅用于预期失败的探测
```

要求：

- fetch/pull/push/rebase/commit/clone 非零退出必须 throw；
- “Already up to date”只能在命令成功时判断；
- timeout、认证失败、remote 不存在、branch 不存在分别返回稳定错误码；
- 禁止只用 stderr 正则推断成功或失败；
- `clearRepo` 任一步失败都不能清空 state 或显示成功。

## 11. SAFE-01：备份与回滚 fail-closed

### 11.1 修复方案

1. 任何将被覆盖或删除的现有文件备份失败时，立即阻止 apply。
2. backup manifest 写入前验证每个数据文件的 hash、mode 和 action。
3. manifest 和 data 使用临时目录完成后再原子 rename。
4. restore 对所有路径复用 `path-safety.ts`。
5. restore 前先完整校验 manifest 和全部 backup data；不允许恢复到一半才发现数据缺失。
6. 自动回滚失败时保留 pending operation 和精确手工恢复路径。
7. backup 只在存在文件变更时创建；单纯 baseline 收敛不创建备份。

## 12. CORE-05：Bootstrap

优先方案：修正脚本，而不是继续把配置仓库作为 package 安装。

新流程：

```text
检查 git/pi
→ pi install npm:@jachy/pi-git-sync@<version>
→ 启动/提示用户运行 /pisync init <repo-url>
```

如果保留自动 clone：

- clone 仅负责配置仓库；
- 不执行 `pi install "${CONFIG_DIR}"`；
- 不硬编码 `main`；
- 所有 URL 和路径作为独立 argv；
- 不忽略 pull 失败；
- fake `pi`/`git` 集成测试覆盖成功和失败路径。

如果无法在 v0.2 前保证脚本可靠，则从 npm `files` 和 README 中移除并标记 deprecated，不能继续发布已知无效入口。

## 13. DEP-01：依赖治理

1. 更新 `@earendil-works/pi-*` 开发/peer 测试解析版本，移除 `brace-expansion@5.0.7`。
2. 评估升级 Vitest/coverage；若 major 升级风险过高，至少通过 override 或受支持的补丁版本清除 high advisory。
3. CI 增加：

```bash
npm audit --omit=dev --audit-level=high
npm audit --audit-level=high
```

生产/peer high 必须为 0。开发 high 原则上也为 0；若上游暂时无修复，必须记录可验证的不可达性、到期时间和 issue，不允许无期限忽略。

- 引入结构化 CommandResult；
- 实现 `preparePush`/`executePush`；
- 修复 capture 后 push、取消后重试、竞态重确认。

- 落实 `config.branch`；
- 修复或移除 bootstrap；
- 清理 high advisory；
- 更新中英文 README、架构文档和升级说明。

退出条件：全部发布门禁通过。

### 16.1 Baseline 与两设备 E2E

- `BASE-01`：修改 tracked 文件并 push，state hash/commit 更新；
- `BASE-02`：首次创建文件并 push，进入 baseline；
- `BASE-03`：删除 tracked 文件并同步，baseline 移除；
- `BASE-04`：converged 文件不写盘但更新 baseline；
- `BASE-05`：A push → B pull → B push → A pull，无伪冲突；
- `BASE-06`：重复命令 no-op，不备份、不 reload、不改时间戳。

### 16.2 Push 状态机

- `PUSH-01`：直接 push；
- `PUSH-02`：capture 后 push；
- `PUSH-03`：取消后重试；
- `PUSH-04`：repo 预先 dirty；
- `PUSH-05`：确认前后 agent/repo 发生变化，旧 preparation 被拒绝；
- `PUSH-06`：capture 后新文件也进入 validation/secret scan；
- `PUSH-07`：direct API 与 Extension 行为一致。

### 16.3 路径安全

- `PATH-01`：root 是绝对 symlink；
- `PATH-02`：root 是相对 symlink；
- `PATH-03`：root 是 dangling/circular symlink；
- `PATH-04`：root 内嵌套文件/目录 symlink；
- `PATH-05`：agent parent symlink；
- `PATH-06`：capture/apply/delete/backup/restore 均不越界；
- `PATH-07`：攻击失败后 repo 外文件 hash、mode、mtime 不变。

### 16.4 Package 信任

- `PKG-01`：新增 npm package 需要审批；
- `PKG-02`：git/HTTPS source 需要审批和固定 revision；
- `PKG-03`：object source 使用同一校验；
- `PKG-04`：路径、控制字符和非法类型被拒绝；
- `PKG-05`：取消时不写 settings、不安装、不 reload；
- `PKG-06`：安装失败触发恢复且不标记成功；
- `PKG-07`：已批准且未变化的 package 幂等；
- `PKG-08`：非交互模式默认拒绝。

### 16.5 Git、分支与 Bootstrap

- `GIT-01`：每个 Git 非零退出都产生 `GitCommandError`；
- `GIT-02`：timeout、认证失败、remote/branch 缺失可区分；
- `BRANCH-01`：自定义分支完整 push/pull；
- `BRANCH-02`：当前分支不匹配且 dirty 时拒绝；
- `BOOT-01`：脚本安装 npm extension，不安装 config repo；
- `BOOT-02`：任一步失败返回非零且不显示成功。

### 16.6 测试与质量门禁

必须执行：

```bash
npm run typecheck
npm test
npm run test:coverage
npm run test:e2e
npm pack --dry-run
npm audit --omit=dev --audit-level=high
```

覆盖率要求：

- 本计划 P0 场景：100% 自动化；
- `state/inventory/materialize/capture/path-safety/backup`：
  Lines/Statements ≥ 95%，Branches ≥ 90%；
- `commands/git/packages`：Lines/Statements ≥ 90%，Branches ≥ 85%；
- 不接受通过降低现有阈值让 CI 变绿。

## 17. 发布与迁移

### 17.1 升级行为

1. 首次加载 v0.2 时备份 state v2 并迁移到 v3。
2. 对 local==repo 的路径自动修复 baseline。
3. 对 local!=repo 的路径不自动选边，status 给出明确冲突。
4. 已安装且 source 未变化的 package 不要求重复安装；新增或变化 source 必须审批。
5. 检测到 repo symlink 时阻止同步并给出迁移指引，不能自动跟随或删除。
6. 检测到当前 Git 分支与 config 不一致时先提示，不在 dirty worktree 上自动 checkout。

### 17.2 发布策略

- 发布 `0.2.0-beta.1`，至少完成 Linux/macOS 双设备 E2E；
- beta 期间重点观察 state migration、package approval 和 Windows symlink 行为；
- 无 P0/P1 回归后发布 `0.2.0`；
- 保留 `0.1.x` state 备份，支持手工降级，但不承诺旧版本理解 state v3。

## 18. 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| state v2 已包含错误 baseline | 只自动收敛两边 hash 相同的路径；不同路径保持冲突 |
| 两阶段 push 在确认期间被外部修改 | HEAD + worktree fingerprint，变化后强制重新准备 |
| 严格 symlink 策略影响少数高级用法 | v0.2 明确不支持 symlink，同步前由 status 报告阻断原因 |
| package 审批增加交互 | 未变化 package 静默通过；支持本地 trust store；非交互输出手工命令 |
| package 安装失败后文件已应用 | 审批前置，安装失败走完整 backup/restore，不提交完成 state |
| Git throw-on-failure 改变旧调用方行为 | 逐个调用点迁移，并为每个失败分支加契约测试 |
| peer 依赖升级引入兼容问题 | beta 验证当前 Pi 主版本，peer 范围改为可测试的兼容区间 |
