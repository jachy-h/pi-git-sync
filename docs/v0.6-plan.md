# pi-git-sync v0.6.0 简洁性与代码组织计划

> 状态：Draft / 目录方案已确认  
> 设计基线：v0.5.1  
> 版本主题：在不改变同步语义与安全边界的前提下，完成编排层收敛，并改善源码导航体验。  
> 最后更新：2026-07-30

## 1. 背景

v0.5 已提取 apply transaction、pull/push integration phase、setup flow 和 operation runner，但编排复杂度尚未完全收敛：

- 生产源码约 9000 行，`src/commands.ts` 约 2694 行，仍占约 30%；
- `pull()`、`preparePush()`、`resolveConflict()` 等方法仍同时处理阶段编排、错误映射和结果展示数据；
- `PiSyncCommands` 仍承担较多 setup、pull、push、conflict 和兼容 wrapper 职责；
- `src/` 下 24 个 TypeScript 文件平铺，按文件名可以定位，但不容易快速理解层次与数据流；
- 已有结构化 `RunResult`，extension 层仍通过 `classifyResult()` 解析 message 文本判断结果类型；
- setup flow 通过多个回调反向连接 façade，边界清晰度与代码简洁性仍可提高；
- branch 检查、失败结果和 preparation 返回对象存在局部重复。

结论：底层同步、安全与恢复机制不是过度设计；v0.6 的优化对象是**编排复杂度、重复样板和导航成本**。

## 2. 版本目标

1. 保持 `/pisync`、`/pisync status`、`/pisync diff`、config schema v2 和 state schema v3 兼容；
2. 让 `PiSyncCommands` 成为真正的薄 façade，只保留公共入口、生命周期、锁边界和顶层顺序；
3. 完整使用结构化结果驱动控制流和通知，不再从 message 文本反推状态；
4. 减少重复错误对象、preparation 对象和 branch/worktree 检查；
5. 收敛 setup flow 与 façade 之间的回调依赖；
6. 采用浅层职责分组组织源码；文件移动与行为重构必须分开提交；
7. 保持依赖图无循环，并让测试目录能够反映生产代码的主要边界。

## 3. 非目标

v0.6 不做以下事情：

- 不重写三方比较、device branch、backup、rollback、package approval 或 secret scan；
- 不引入状态机框架、依赖注入容器、事件总线、command bus 或 service class hierarchy；
- 不为单个小 helper 建立目录或 barrel export；
- 不为了减少行数增加无意义 wrapper；
- 不在同一提交中同时移动文件和修改同步行为；
- 不在未经独立确认的实施阶段批量移动 `src/` 或 `test/` 文件。

## 5. 源码组织方案（待讨论）

### 方案 A：保持平铺，仅强化命名

```text
src/
├── commands.ts
├── sync-pull-flow.ts
├── sync-push-flow.ts
├── sync-apply-transaction.ts
├── setup-flow.ts
├── git.ts
└── ...
```

**优点**：移动成本最低，import 简单，不会产生目录层级争议。  
**缺点**：文件继续增长后导航问题仍存在，无法直观看出 extension、orchestration、sync engine 与 system adapter 的边界。

### 方案 B：按技术层分目录

```text
src/
├── application/
├── domain/
├── infrastructure/
└── presentation/
```

**优点**：形式标准，依赖方向容易描述。  
**缺点**：名称偏抽象；查一个同步流程时需要跨多个目录跳转，容易演变为不必要的“Clean Architecture”仪式。

### 方案 C：浅层、职责导向分组（已确定）

```text
index.ts                         # Pi package 入口保持根目录
src/
├── orchestration/               # 流程、事务、结果与 façade
│   ├── commands.ts
│   ├── operation-context.ts
│   ├── operation-result.ts
│   ├── setup-flow.ts
│   ├── pull-flow.ts
│   ├── push-flow.ts
│   ├── apply-transaction.ts
│   └── conflict-flow.ts           # 高层冲突协调
├── sync/                        # 配置文件比较与双向镜像核心
│   ├── config.ts
│   ├── glob.ts
│   ├── inventory.ts
│   ├── capture.ts
│   ├── materialize.ts
│   ├── settings-portability.ts
│   └── validate.ts
├── system/                      # Git、持久化与本机副作用边界
│   ├── git.ts
│   ├── state.ts
│   ├── backup.ts
│   ├── lock.ts
│   ├── packages.ts
│   ├── path-safety.ts
│   ├── security.ts
│   └── conflict-resolution.ts     # 低层 Git 冲突事务
└── extension/                   # Pi/TUI 适配
    ├── operation-runner.ts
    └── ui.ts
```

对应测试可逐步整理为：

```text
test/
├── orchestration/
├── sync/
├── system/
├── extension/
├── helpers/
└── e2e/
```

**优点**：

- 只增加一层目录，避免深层嵌套；
- 按“流程 / 同步核心 / 系统副作用 / Pi 适配”即可理解大部分文件；
- 与当前真实边界接近，不需要建立新 class 或 interface；
- `index.ts → extension/orchestration → sync/system` 的依赖方向较直观。

**风险**：

- `packages.ts`、`security.ts` 等跨领域文件需要在架构文档中明确边界，避免职责继续扩张；
- 仅移动文件不会降低复杂度，必须与后续 flow 收敛分开衡量；
- 一次性同步移动全部测试会产生较大 diff，建议分批执行。

### 决策记录

v0.6 确定采用**方案 C**，使用 `orchestration / sync / system / extension` 四个浅层职责目录，不引入更深的技术分层。

具体约束：

1. `index.ts` 继续位于项目根目录，作为 Pi package 入口；
2. 高层 conflict coordination 位于 `orchestration/conflict-flow.ts`，低层 Git conflict transaction 位于 `system/conflict-resolution.ts`；
3. 第一阶段只移动生产代码，测试目录在边界稳定后再逐步镜像；
4. 移动前先明确 `pull-flow.ts`、`push-flow.ts` 的职责，但不在纯移动提交中提取或修改逻辑；
5. 不建立 barrel files，继续使用显式 import。

实施顺序固定为：**确认文件映射 → 纯移动 commit → 验证 import/CI → 再做行为不变的 flow 重构**。
